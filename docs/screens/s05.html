Serving size multiplication — most error-prone feature
// WRONG — shows "1.5 tomatoes", "0.67 tsp" qty_display = base_qty * servings // CORRECT — round with display logic function formatQty(base, servings) { const raw = base * servings if (unit === 'pcs') { return Math.ceil(raw) // always round up } if (unit === 'tsp' || unit === 'tbsp') { // show fractions: 0.25→¼, 0.5→½, 0.75→¾ return toFractionString(raw) } if (unit === 'g' || unit === 'ml') { return Math.round(raw / 5) * 5 // round to 5g } return raw }
Other pitfalls
  • Fork vs bookmark: Fork creates a new row in templates with creator_id = current user. It is NOT a saved/bookmarked reference to the original. The fork can be edited independently.
  • fork_count optimistic update: Increment fork_count on the UI immediately on click. Sync to server async. Never wait for the API — the user already clicked and the modal is open.
  • "Add to Instamart" vs "Add to plan": "Add to Instamart" calls cart/build and navigates to Cart Preview. "Add to plan" calls meal-plans/slots and shows a dropdown. These are entirely separate flows — never merge them.
  • Similar templates N+1: The response includes similar_template_ids — a pre-computed list. Never compute similarity at query time. Run a background job nightly.
  • Instamart qty mismatch: Instamart sells spinach in 250g packs but the ingredient calls for 80g. The cart/build endpoint handles this rounding. Never expose raw qty to the Instamart API without first aligning to pack sizes.
Visibility and creator privacy
  • Public templates (is_public=true): no auth required. Cache at CDN edge — Vercel will cache GET /api/templates/:id for 60s.
  • Creator field: return only display_name. Never return email, clerk_id, or full name. The creator deliberately chose a display name.
  • Fork endpoint: auth required. Validate that the source template is public OR the requester is the creator. A user cannot fork a private template they don't own.
  • est_cost_per_serving: computed server-side from Instamart price data. Never editable by the creator — it reflects real Instamart prices, not a declared cost.
Swiggy DS — detail page rules
  • Kcal is the hero number. 380 in orange, large. First number in the stats row. This is what users scanned the card for — confirm it immediately.
  • Buy count is stronger proof than fork count. "847 people added to Instamart" means 847 people bought real groceries. Show it in the social proof bar below the stats.
  • Three CTAs, strict hierarchy: "Add to plan" (primary orange), "Fork" (outline), "Add to Instamart" (text link only). Never three filled buttons.
  • Fork opens a modal, not a page. The modal confirms the fork and offers "Stay here" or "Edit my version". This keeps the user in the discovery flow.
  • Serving size toggle: − / number / + control, not a slider. Sliders are imprecise for discrete values like "2 people". Place it in the ingredient panel header.
  • Ingredient availability tag: "On Instamart" in green next to each item. This is a strong purchase signal — it tells the user the ingredient is actually available right now.
  • Mobile tabs: Ingredients | Instructions | Nutrition. Default tab is Ingredients. The CTA bar is always sticky at the bottom regardless of which tab is active.
  • Similar templates: Compact list rows, not full cards. Three is enough. More reduces focus on the primary action.
